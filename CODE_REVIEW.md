## 1. Executive Summary

Проект аккуратно написан и хорошо структурирован для своего размера: разделение `routes/` / `services.py` / `schemas.py` выдержано, все SQL-запросы параметризованы, соединения к БД закрываются в `finally` во всех девяти маршрутах, рендер карточек на фронтенде защищён от XSS через `textContent`, а реконсилирующий рендер и `AbortController` для подсказок поиска сделаны на уровне, который редко встречается в pet-проектах. Ноль TODO/FIXME, ноль закомментированного кода, осмысленные комментарии «почему, а не что».

При этом **проект не готов к выставлению наружу** и содержит два дефекта, приводящих к потере пользовательских данных при штатном использовании. Главный архитектурный пробел — полное отсутствие аутентификации в сочетании с `allow_origins=["*"]` и `allow_credentials=True`: любой сайт, открытый в браузере пользователя, может читать и перезаписывать все данные приложения на `localhost`. Это превращает каждую последующую находку из локальной в удалённо эксплуатируемую. Самая тяжёлая из них — цепочка из трёх независимо найденных дефектов, дающая **произвольное удаление файлов двумя запросами без авторизации** (невалидируемый `background_image` + `os.path.join` с абсолютным путём + контейнер от root). Отдельно: SSRF в фетчере фавиконок не «слепой», а с полным чтением ответа — содержимое внутреннего эндпоинта сохраняется в `uploads/` и вычитывается атакующим.

Функциональных потерь данных две, обе воспроизводятся в один клик: движение слайдера блюра или переключение темы физически удаляет файл обоев (Pydantic не различает «поле не передано» и «поле = null»), а редактирование любой карточки стирает её иконку и сбрасывает размер `2x2` на `1x1` (состояние модалки живёт в closure-переменных, которые обработчик редактирования не обновляет). Тестов в репозитории нет ни одного, статического анализа нет, CI нет, зависимости не запинены — при наличии ручных миграций схемы с `DROP TABLE` и безусловного `DELETE FROM cards` в импорте это означает, что любая регрессия в деструктивных путях пройдёт незамеченной.

Документация отстала от кода примерно на два коммита и в разделе «Безопасность» описывает защиту, которой фактически нет. Отдельно опасен `README.md:43`: задокументированная команда `docker run` монтирует том не туда, куда пишутся данные, — пользователь теряет БД при первом же обновлении образа и вдобавок получает замороженный старый код.

**Вердикт по готовности.** Для личного использования на `127.0.0.1` — пригодно после починки двух багов с потерей данных. Для доступа из локальной сети — только после аутентификации и починки path traversal. Для публичного интернета — не пригодно в текущем виде; требуется весь блок Critical + аутентификация + reverse proxy с TLS и rate limiting.

**Оценка объёма работ:** Critical + High ≈ 2–3 дня; добавление тестов на деструктивные пути ≈ 2 дня; полный список Medium ≈ ещё неделя.

Главный блокер — не отсутствие тестов, а то, что **код в текущем виде трудно тестировать**:

1. `database.py:5` — `DATABASE_PATH` вычисляется на импорте.
2. `services.py:17` + `from services import UPLOADS_DIR` в `routes/cards.py:8`, `routes/uploads.py:6`, `routes/settings.py:7`, `routes/data.py:12` — **связывание по значению на момент импорта**. `monkeypatch.setattr("services.UPLOADS_DIR", ...)` не повлияет ни на один маршрут; патчить нужно шесть мест, иначе тесты будут писать в реальный `backend/uploads/`.
3. `main.py:23` дублирует вычисление `UPLOADS_DIR` независимо от `services.py:17`.
4. Нет `backend/__init__.py`, импорты абсолютные top-level — тестам нужен `pythonpath = ["backend"]`.
5. `services.py:150` — `httpx.AsyncClient` создаётся внутри `fetch_favicon`, подменить нечем.

Минимальный рефакторинг (полдня) — вынести конфигурацию в `config.py` с функциями-геттерами вместо констант, принимать `client` параметром в `fetch_favicon`. После этого тесты пишутся тривиально.

### 5.4. Стоит ли пересматривать технологические решения

**ORM — не нужен.** Схема из двух таблиц, запросы простые, SQL параметризован корректно. Введение SQLAlchemy добавит зависимость и слой абстракции ради нулевой выгоды. А вот **Alembic или хотя бы `PRAGMA user_version`** — нужны: текущие ad-hoc-миграции (H6) реально опасны и уже содержат сценарий невосстановимого падения старта.

**ES-модули — да, стоит.** Не ради моды: `app.js` на 779 строк с циклической зависимостью через `window.App` (L15) и дублированием логики (L16, M38) — прямое следствие отсутствия явных импортов. Переход на `<script type="module">` не требует сборщика и не ломает «без сборки»-подход, а даёт явные границы и устраняет глобальный неймспейс. Это единственное фронтенд-решение из README, которое я бы пересмотрел.

**Слой аутентификации — обязателен**, если проект вообще предполагает сетевой доступ. Минимально достаточно одного общего токена в env + middleware на `/api/*` кроме health. Полноценные пользователи не нужны — приложение однопользовательское по дизайну (таблица `settings` из одной строки).

**SQLite — правильный выбор** для однопользовательского приложения, но текущая конфигурация (без WAL, без `busy_timeout`) рассчитана строго на один воркер. Это надо либо зафиксировать в документации как ограничение, либо починить (H5). Сейчас README активно ведёт пользователя в противоположную сторону.

**Три способа хранить порядок карточек** (M13) — самая заметная архитектурная неопрятность. `position` не читается никогда и гарантированно расходится с гридом после первого перетаскивания. Выбрать один источник истины.

```python
def safe_upload_path(name: str) -> str:
    """Единственный разрешённый способ получить путь внутри UPLOADS_DIR."""
    if not name or "\x00" in name:
        raise HTTPException(400, "Invalid filename")
    base = os.path.realpath(UPLOADS_DIR)
    candidate = os.path.join(base, name)
    if os.path.islink(candidate):
        raise HTTPException(400, "Invalid filename")
    resolved = os.path.realpath(candidate)
    if os.path.commonpath([base, resolved]) != base:
        raise HTTPException(400, "Invalid filename")
    return resolved


def _safe_unlink(path: str) -> None:
    try:
        os.remove(path)
    except FileNotFoundError:
        pass
    except OSError:
        logger.warning("failed to unlink %s", path, exc_info=True)
```

2. **SSRF через DNS rebinding (M2).** Требует контролируемого DNS с TTL=0 (например, `rebind.network`). Отличить «уязвимо» от «не уязвимо» по коду нельзя — только экспериментом.
3. **Path traversal (C2).** `PUT /api/settings {"background_image":"/app/data/homepage.db"}`, затем `PUT /api/settings {"dark_mode":true}`. **Делать только на одноразовом контейнере** — при подтверждении БД будет удалена.
4. **Обход фильтра схем (C5).** `POST /api/cards {"url":"java\tscript:alert(1)","open_in_new_tab":false}`, затем клик по карточке в реальном браузере. Проверить в Chrome и Firefox отдельно — нормализация схемы может отличаться.
5. **SVG XSS (H1).** Загрузить SVG со `<script>`, открыть `/api/uploads/<uuid>.svg` напрямую и убедиться, отрабатывает ли скрипт.
6. **`::ffff:127.0.0.1` в `is_private` (M1, ТРЕБУЕТ ПРОВЕРКИ).** Корректная обработка появилась только в CPython 3.11.10/3.12.4+ (gh-113171). Проверить в фактическом образе: `docker run --rm thuleseeker/thule:latest python -c "import ipaddress;print(ipaddress.ip_address('::ffff:127.0.0.1').is_private)"` — должно быть `True`.
7. **Потеря обоев (C3).** Загрузить фон, подвигать слайдер блюра, обновить страницу. Ожидается исчезновение фона и отсутствие файла в `uploads/`.
8. **Потеря иконки и размера (C6).** Создать карточку `2x2` с загруженной иконкой, нажать «Edit», ничего не меняя нажать «Save». Ожидается `1x1` без иконки.
9. **`database is locked` (H5).** Запустить с `--workers 4` и параллельно перетащить несколько карточек. Проверить логи на `OperationalError`.
10. **Замороженный код в named volume (H7).** Именно этот эффект диагностируется хуже всего: `docker run -v thule-data:/app/backend` образом 1.0.0, затем `docker pull` 1.1.0 и пересоздание — проверить, какая версия реально работает (по наличию поля `open_in_new_tab` в UI, так как `/api/health` врёт из-за L9).
11. **Вёрстка в диапазоне 769–1024px (H20).** Создать карточку с `grid_col=6`, плавно менять ширину окна. Ожидается выход за границы сетки.
12. **Клавиатурная доступность (H16, M25).** Пройти весь сценарий (открыть карточку, создать, отредактировать, закрыть модалку) только с клавиатуры, затем прослушать в скринридере.
13. **Многоархитектурность образа (M32).** Проверить, запускается ли `thuleseeker/thule:latest` на arm64 — типовая аудитория homepage-приложений сидит на Raspberry Pi.
14. **Совместимость с Python 3.10 (M34).** README заявляет 3.10+, образ собран на 3.12. Прогоном не проверялось.

### 9.2. Разрешённые противоречия между ревью

Пять независимых ревью в трёх случаях разошлись в оценках; расхождения проверены вручную:

| Вопрос | Расхождение | Проверка и вывод |
|---|---|---|
| Корректность ignore-файлов | Одно ревью: «оба корректны»; другое: «`.dockerignore` дырявый» | **Правы оба частично.** `.gitignore` корректен: git матчит `*.db` на любой глубине + есть явный `backend/homepage.db`. `.dockerignore` некорректен: Docker применяет `filepath.Match` посегментно, `*.db` покрывает только корень, `backend/homepage.db` не покрыт, `uploads/` и `homepage-data/` не упомянуты. Зафиксировано как H9 |
| Экранирование в `_esc()` | Одно ревью: «XSS закрыт»; другое: «атрибутная инъекция, High» | **Право второе.** Сериализация текстового узла в `innerHTML` экранирует `&`, `<`, `>`, но не `"`, а результат подставляется в `data-q="..."`. Зафиксировано как H12. Первое ревью оценивало `card-title` (`textContent`) — там действительно закрыто |
| Тяжесть fail-open в `is_private_ip` | Оценки Critical / High / Low от трёх ревью | **Свёл к Medium (M1).** Прямая эксплуатация ограничена: если `getaddrinfo` не резолвит имя, httpx тоже не подключится. Но семантика инвертирована относительно собственных комментариев кода и сломается при рефакторинге. Реальный риск сосредоточен в C4 (редиректы и `urljoin`), где он уже учтён |

Дополнительно: три ревью независимо вышли на дефект `background_image` с трёх сторон — как на функциональную потерю данных (C3), как на path traversal (C2) и как на расхождение документации с кодом. Это один и тот же корневой дефект, сведён в связанную пару находок.
