# Аудит фронтенда thule-homepage — разбор поломки раскладки и полный анализ

**Дата:** 2026-09-11 · **Коммит на момент анализа:** `3f4f0aa` · **Версия:** 1.2.1
**Инцидент:** после открытия `https://homepage.thulefinder.uk` с мобильного телефона раскладка карточек на десктопе схлопнулась в одну колонку.

Этот документ — передача задачи другому агенту. Изменений в код **не вносилось**. Все находки привязаны к строкам.

---

## 0. Прочитай это первым: данные уже потеряны

Раскладка не «отображается неправильно» — **позиции карточек перезаписаны в базе на сервере**. Починка кода сама по себе layout не вернёт.

Порядок действий для исполнителя:

1. **Сначала останови кровотечение.** Пока баг в коде, любой следующий заход с телефона снова перезапишет позиции. Если чинить не сразу — предупреди пользователя не открывать сайт с мобилы.
2. **Потом восстанови данные.** Варианты по убыванию предпочтительности:
   - экспорт-бэкап JSON (кнопка Export в настройках), если он есть у пользователя;
   - копия `homepage.db` на сервере (`./homepage-data/homepage.db` рядом с compose-файлом), в т.ч. WAL-файлы;
   - ручная расстановка заново.
3. **Импорт бэкапа выполнять только с десктопа.** При текущем коде импорт с узкого экрана немедленно прогонит данные через тот же деструктивный путь (см. FE-08) и угробит их повторно.

## 1. Корневая причина (FE-01, Critical)

### 1.1 Однострочная формулировка

`_autoSpreadCards()` трактует **количество колонок в текущем вьюпорте** как **ширину модели данных** и записывает результат перепаковки на сервер. На телефоне вьюпорт — 1 колонка, поэтому все карточки переезжают в `grid_col = 1` и это сохраняется навсегда.

### 1.2 Цепочка выполнения

| Шаг | Файл:строка | Что происходит |
|---|---|---|
| 1 | `frontend/js/app.js:19` | `this.gridCols = 7` — стартовое значение |
| 2 | `frontend/js/app.js:55` | `init()` вызывает `_detectGridCols()` **до** загрузки данных |
| 3 | `frontend/js/app.js:40-45` | `getComputedStyle(grid).gridTemplateColumns.split(' ').length` → на телефоне `1`…`3` |
| 4 | `frontend/js/app.js:60` → `:774` | `loadData()` → `this._autoSpreadCards()` |
| 5 | `frontend/js/app.js:795` | `const cols = Math.max(1, this.gridCols)` — берёт **вьюпортное** значение |
| 6 | `frontend/js/app.js:801` | `fits()`: `if (col < 1 \|\| row < 1 \|\| col + w - 1 > cols) return false` — любая карточка с `grid_col ≥ 2` не проходит |
| 7 | `frontend/js/app.js:822-835` | все «не влезшие» перепаковываются в колонки `1..cols`, строки `1..N`; локальное состояние мутируется |
| 8 | `frontend/js/app.js:840` | `this._persistMoves(moves)` |
| 9 | `frontend/js/app.js:843-846` | `api.updateCard(id, {grid_col, grid_row})` на каждую карточку — **запись на сервер** |

### 1.3 Соответствие брейкпоинтов и разрушения

| Ширина вьюпорта | `grid-template-columns` | `gridCols` | Результат в БД |
|---|---|---|---|
| > 1024px | `repeat(7, …)` (`styles.css:359`) | 7 | корректно |
| ≤ 1024px | `repeat(4, …)` (`styles.css:1131`) | 4 | колонки 5–7 потеряны |
| ≤ 768px | `repeat(3, …)` (`styles.css:1203`) | 3 | колонки 4–7 потеряны |
| ≤ 480px | `repeat(2, 1fr)` (`styles.css:1370`) | 2 | колонки 3–7 потеряны |
| ≤ 380px | `1fr` (`styles.css:1593`) | 1 | **всё в колонку 1** |

Скриншот показывает три карточки в колонке 1, строках 1–3 — это ровно сценарий `gridCols = 1`, то есть телефон с CSS-шириной ≤ 380px (iPhone SE, 360px-Android, либо увеличенный системный масштаб шрифта).

### 1.4 Почему CSS-сброс не спас

В каждом мобильном брейкпоинте есть правило вида

```css
.card { grid-column: auto !important; grid-row: auto !important; }
```

(`styles.css:1136-1138`, `1210-1212`, `1377-1379`)

Оно делает **визуальную** раскладку на мобильном корректной. Но JS не смотрит на это правило вообще: `_autoSpreadCards` работает с числами из `getComputedStyle` и пишет их в модель. То есть CSS честно говорит «на мобильном позиции игнорируются», а JS в это же время считает их истиной и сохраняет. Баг чисто в JS-слое.

### 1.5 Дополнительная подлость

`_persistMoves` (`app.js:859`) показывает тост `Spread N overlapping cards` — зелёный, успешный. Пользователь на телефоне видел сообщение об успехе в момент, когда его раскладку затирали. Ни название функции, ни текст тоста не отражают того, что реально произошло: перепаковываются не «перекрывающиеся» карточки, а все, кто не влез в узкий вьюпорт.

### 1.6 Архитектурный дефект под багом

Одна переменная `this.gridCols` обслуживает две несовместимые роли:

- **ширина модели данных** — канонические 7 колонок, совпадает с `backend/config.py::COLS_PER_ROW`, ограничена схемой `grid_col: int = Field(ge=1, le=config.COLS_PER_ROW)` (`backend/schemas.py:35,61`);
- **ширина представления** — сколько колонок реально рисует CSS при текущей ширине окна.

Пока эти роли не разделены, любая правка будет затыканием симптома. Канон — 7, и он не должен зависеть от того, с какого устройства зашли.

## 2. Воспроизведение

```
1. Десктоп: расставить карточки по колонкам 1–7. Убедиться, что grid_col различаются
   (GET /api/cards или Export).
2. Открыть тот же адрес с телефона (или DevTools → device toolbar → iPhone SE 375px,
   обязательно перезагрузить страницу — ресайза недостаточно, см. §3 FE-10).
3. Наблюдать тост "Spread N overlapping cards".
4. Вернуться на десктоп, F5.
5. Все карточки в колонке 1.
```

Проверка без UI: `GET /api/cards` до и после шага 2 — `grid_col` у всех станет `1`.

## 3. Все находки

Формат: `[Severity] ID — Файл:строка — Проблема — Почему это проблема`.

### Critical

**FE-01 · `frontend/js/app.js:795,801,840`**
Вьюпортное число колонок используется как ширина модели и результат перепаковки пишется на сервер. Разбор — §1. Один визит с мобильного необратимо уничтожает десктопную раскладку.

**FE-02 · `frontend/js/app.js:337-343` + `styles.css:1136-1138,1210-1212,1377-1379`**
Drag & drop на мобильном пишет бессмысленные координаты. `_calcGridPos` вычисляет колонку/строку из пиксельной геометрии сетки, но на мобильном карточки размещены автопотоком (`grid-column: auto !important`), поэтому визуальная позиция карточки никак не связана с её хранимыми `grid_col/grid_row`. Перетаскивание на телефоне сохраняет координаты, соответствующие месту в потоке, а не в модели. Это **второй независимый вектор** той же потери данных — закрытие только FE-01 его не устраняет.

### High

**FE-03 · `frontend/js/components.js:192-229` + `styles.css:1136-1138`**
Плейсхолдеры сетки в edit-mode ломают раскладку на мобильном. `_renderGridCells` проставляет `.grid-cell` инлайновые `gridColumnStart/End`, `gridRowStart/End` (`components.js:218-221`). Медиазапросы сбрасывают позиции **только у `.card`**, `.grid-cell` не сбрасывается нигде. В итоге на мобильном ячейки занимают строки 1..maxRow явно, а карточки автопотоком выталкиваются **под них**. Визуально: сначала столбик пустых пунктирных прямоугольников, потом карточки. Плюс `elementFromPoint` во время drag попадает в ячейку, чьи `data-col/data-row` не соответствуют ничему на экране.

**FE-04 · `frontend/js/app.js:339`**
`_calcGridPos()` — геометрический хелпер — молча мутирует состояние приложения: `this.gridCols = m.cols;`. Побочный эффект в функции-вычислителе; вызывается из `moveDrag` на каждом кадре перетаскивания. Меняет клэмп в `_findFreeSpot` (`app.js:421`) для всех последующих операций.

**FE-05 · `frontend/js/app.js:40-45`**
Парсинг `gridTemplateColumns` через `split(' ').length` хрупкий и не валидируется. Для отрисованного элемента возвращается resolved-значение (`140px 140px …`) и всё работает, но:
- если элемент окажется `display:none`, вернётся *specified*-значение `repeat(7, minmax(140px, 1fr))` → `split(' ')` даст `3` → `gridCols = 3` без единого признака ошибки;
- любое будущее правило с `repeat(auto-fill, …)` даст тот же тихий сбой;
- нет проверки вменяемости результата и нет фолбэка.

**FE-06 · три источника константы «7»**
`frontend/js/app.js:19`, `frontend/js/components.js:140` (`cols = 7` в дефолтном параметре), `frontend/index.html:180` (`max="7"`), при том что бэкенд уже централизовал её в `backend/config.py::COLS_PER_ROW`. Рассинхрон при изменении неизбежен. Это незакрытый остаток находки M14 из `CODE_REVIEW.md` — бэкенд привели к одной константе, фронтенд нет.

### Medium

**FE-07 · `frontend/js/app.js:843-861`**
`_persistMoves` шлёт N параллельных PUT без батчинга и без предусловий. При 20 карточках — 20 запросов на старте. Нет проверки, что пользователь аутентифицирован и что сеть доступна: при `AUTH_TOKEN` и отсутствующем токене получим пачку 401 и тост об ошибке поверх модалки логина. Напрашивается батч-эндпоинт (на бэкенде уже есть `POST /api/cards/reorder`).

**FE-08 · `frontend/js/app.js:774` в связке с `:998`**
`_autoSpreadCards()` вызывается в каждом `loadData()`, в том числе после `_import()`. Импорт десктопного бэкапа с мобильного вьюпорта немедленно прогоняет данные через FE-01 и перезаписывает их. Именно поэтому восстановление из бэкапа обязано выполняться с десктопа (см. §0).

**FE-09 · `frontend/js/app.js:529-537` + `:589`**
Нельзя очистить Icon URL, стерев поле. Обработчик `input` обновляет `_modalState.iconFile` только при непустом значении (`if (v) { … }`, без `else`). При сохранении `icon_path: typedIconUrl || this._modalState.iconFile || null` (`:589`) пустая строка падает в фолбэк и подставляет старый URL. Очистка возможна только кнопкой remove.

**FE-10 · `frontend/js/app.js:63-67`**
Обработчик `resize` делает `_detectGridCols()` + `renderCards()`, но не перезапускает spread — поведение при ресайзе и при загрузке разное. Сейчас это единственное, что спасает от разрушения данных при обычном изменении размера окна на десктопе, но это случайность, а не намерение: `_detectGridCols` при этом всё равно меняет `gridCols`, и следующий drag будет клэмпиться уже по новому значению.

**FE-11 · `frontend/index.html:180`**
`max="7"` в поле Column захардкожен и на мобильном вводит в заблуждение: поле есть, значение принимается, но на узком вьюпорте позиция игнорируется CSS-ом и будет затёрта.

**FE-12 · `frontend/js/components.js:289-313`**
Восстановление фокуса ломается при наложении модалок. `showModal` безусловно перезаписывает `Components._lastFocused`; если поверх настроек открыть модалку карточки, закрытие вернёт фокус не туда. `setTimeout(() => target.focus(), 50)` (`:301`) — гонка с CSS-переходом, а не привязка к `transitionend`.

**FE-13 · `frontend/js/components.js:340`**
`dragleave` на области загрузки сбрасывает подсветку при уходе указателя на любой дочерний элемент — рамка мигает при перетаскивании файла внутри зоны.

### Low

**FE-14 · `frontend/js/components.js:10-19`** — `safeUrl` резолвит относительно `window.location.origin`, поэтому URL `foo` превращается в ссылку на сам сайт вместо отбраковки. Схема безопасна, но поведение неожиданное.

**FE-15 · `frontend/css/styles.css:399-401`** — `transition: grid-column …, grid-row …` — эти свойства не анимируются; мёртвый CSS.

**FE-16 · `frontend/js/app.js:927`** — нативный `confirm()` для удаления карточки: блокирующий диалог, выбивается из модальной системы, не стилизуется, на мобильном выглядит чужеродно.

**FE-17 · `frontend/index.html:10`** — Google Fonts подключён синхронным `<link rel="stylesheet">`: внешняя зависимость в критическом пути рендера. При недоступности CDN первый показ задерживается.

**FE-18 · `frontend/js/components.js:315-324`** — один общий таймер тоста: быстрая серия сообщений обрезает предыдущие, последнее перетирает текст на лету.

**FE-19 · `frontend/index.html:45` + `components.js:253-267`** — у контейнера подсказок `role="listbox"`, у элементов `role="option"`, но нет `aria-activedescendant` и нет навигации стрелками. Для скринридера объявлен listbox, которым нельзя управлять с клавиатуры.

**FE-20 · `frontend/css/styles.css:1640-1643`** — анимация `slideUp` применяется ко всем карточкам без учёта `prefers-reduced-motion`.

**FE-21 · `backend/main.py:34`** — CSP разрешает `img-src … http:`, но сайт отдаётся по HTTPS, поэтому `http:`-иконки всё равно заблокируются правилами mixed content. Разрешение в CSP вводит в заблуждение и ничего не даёт.

**FE-22 · `frontend/js/app.js:963-975`** — `_export()` вызывает `link.click()` без вставки элемента в DOM. В современных браузерах работает, исторически в Firefox требовалась вставка.

## 4. Дыра в тестах, из-за которой баг доехал до продакшена

`tests/js/drag.test.js` покрывает планирование перемещений и авто-spread, но **всегда** фиксирует `app.gridCols = 7` (`drag.test.js:44`, `:124`). Тест `spreads overlapping 2x2 cards without leaving gaps in the occupancy` (`:94-108`) проверяет именно `_autoSpreadCards` — и делает это только на семиколоночной сетке.

Сценарий «узкий вьюпорт» не покрыт ни одним тестом. Все 26 vitest-тестов проходят, потому что мобильного случая в наборе нет.

Минимум, который обязан появиться вместе с фиксом:

- `_autoSpreadCards` при `gridCols = 1` (и 2, 3, 4) **не меняет** `grid_col`/`grid_row` карточек, которые не перекрываются в модели на 7 колонок;
- `_persistMoves` **не вызывается**, если реальных коллизий в модели нет;
- перетаскивание при узком вьюпорте либо запрещено, либо оперирует модельными координатами;
- `_detectGridCols` при нераспарсенном/невалидном значении откатывается к канону, а не к длине строки;
- регрессия «полный цикл»: смонтировать с 7-колоночной раскладкой → эмулировать вьюпорт 375px → перезагрузить → позиции в модели идентичны исходным.

## 5. Направление исправления (не реализовано, на усмотрение исполнителя)

Ключевое требование: **развести модель и представление**.

- Ввести канон `MODEL_COLS`, синхронный с `backend/config.py::COLS_PER_ROW` (7). Отдавать его клиенту с бэкенда — например, в `GET /api/full-data` или `/api/health` — чтобы константа осталась в одном месте и закрылась FE-06.
- `_autoSpreadCards`, `_planMove`, `_findFreeSpot`, валидация поля Column — работают **только** с `MODEL_COLS`, всегда, независимо от вьюпорта.
- `_detectGridCols` переименовать в нечто вроде `_detectViewportCols` и использовать исключительно для hit-testing при drag на десктопе.
- Ввести явный флаг «вьюпорт уже модели» (`viewportCols < MODEL_COLS`). В этом состоянии: drag & drop либо выключается, либо переводится в режим переупорядочивания списка (`/api/cards/reorder`), но **не** пишет `grid_col/grid_row`; edit-mode-плейсхолдеры (`.grid-cell`) не рендерятся вовсе — это заодно закрывает FE-03.
- `_autoSpreadCards` должен запускать `_persistMoves` только при реальных коллизиях в модели, а не при каждом несоответствии вьюпорту. Тост переформулировать так, чтобы он честно описывал изменение данных.

Отдельно: решить, нужен ли `_autoSpreadCards` на клиенте вообще. Разрешение коллизий — инвариант данных, ему место на бэкенде при записи, где нет никакого вьюпорта и где это невозможно испортить с телефона.

## 6. Что проанализировано и что нет

**Проанализировано полностью:**
`frontend/js/app.js` (1006 строк), `frontend/js/components.js` (363), `frontend/js/api.js` (156), `frontend/js/theme-init.js` (8), `frontend/index.html` (274). `frontend/css/styles.css` (1670) — разобраны сеточные правила и все четыре брейкпоинта; `backend/schemas.py`, `backend/config.py`, `backend/main.py` — в части, относящейся к ограничениям сетки и CSP.

**Не проанализировано:**

- `frontend/css/styles.css` вне сеточных правил и медиазапросов — цветовая система, компоненты форм, модалки, скроллбары (~1100 строк). Может содержать дополнительные визуальные дефекты на мобильном.
- Поведение в реальном браузере не проверялось: сборки/запуска не делал, скриншотов не снимал. Все выводы — статический анализ кода. FE-03 выведен логически из каскада и автопотока grid, в браузере не подтверждён.
- a11y-аудит скринридером не проводился.
- Кросс-браузерность (Safari iOS, в частности Pointer Events и `setPointerCapture`) не проверялась.
- Текущее состояние продакшен-базы не инспектировалось — объём потерь не измерен.
